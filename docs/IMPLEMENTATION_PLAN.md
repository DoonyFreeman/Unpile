# План реализации

План разработки. Подготовлена нативная локальная beta 0.7.0 с UI, чтением папки, сохранением сессий, English/Русский, системным Quick Look, проверкой списка и переносом в Корзину. Есть оригинальная иконка, Universal DMG и материалы открытого репозитория; в 0.6 добавлены phased trackpad swipes и фиксированная панель решений. Точное состояние этапов и выполненные проверки — в [PROGRESS.md](PROGRESS.md). Остальные требования ниже описывают целевую v1.0, а не утверждают, что она уже готова.

## 1. Стек и ограничения

Рекомендация: **Swift + SwiftUI**, точечные AppKit-интеграции для выбора папки, Quick Look, меню, keyboard focus и Finder. Для этой утилиты нативный доступ и ощущение macOS важнее общей кодовой базы с другими платформами. Сервер и Node/Electron-runtime в поставке не нужны.

Предварительно macOS 14+; поддержка Apple Silicon и Intel одним Universal-бинарником. Закрепить точный Xcode/Swift toolchain после первой пробы и проверить все используемые API на минимальном deployment target. Не обещать Intel, пока нет проверки на соответствующем устройстве или подходящем CI и пользовательском пилоте.

App Sandbox включён с первого прототипа. По [документации Apple о доступе к файлам](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox) использовать системный выбор папки, разрешение user-selected read-write и security-scoped bookmarks для повторного доступа. Уравновешивать start/stopAccessingSecurityScopedResource; обрабатывать устаревший bookmark. Наличие bookmark не отменяет POSIX/ACL и другие ограничения доступа.

Превью: [QLThumbnailGenerator](https://developer.apple.com/documentation/quicklookthumbnailing/qlthumbnailgenerator) для проверенного allowlist типов, локальный Quick Look через AppKit. Для активных/неподдерживаемых типов — метаданные. Кэш приложения ограниченный в памяти, 2–3 миниатюры вперёд; исключить чтение файла целиком ради вывода размера.

Перенос: только [FileManager.trashItem(at:resultingItemURL:)](https://developer.apple.com/documentation/foundation/filemanager/trashitem(at:resultingitemurl:)). Apple предупреждает, что имя в Корзине может измениться; полученный URL нельзя угадывать по исходному имени. В v1.0 восстановление делается пользователем через Finder, не через запись в .Trash.

Первая обязательная техническая проба: выбрать папку → сохранить доступ → перезапустить → показать превью → перенести синтетический файл в Корзину в sandbox-сборке с доступной бесплатной локальной/ad hoc подписью. Проверить выбранный способ упаковки и поведение доступа при обновлении такой сборки. Платный Developer ID не является условием этой пробы. Доступ к Корзине и Quick Look нельзя считать решёнными только по API-описанию.

Визуальная цель — macOS 27 / Liquid Glass. Использовать системные controls/materials и API с availability-checks; сохранить fallback на минимальной поддерживаемой OS. Новое оформление само по себе не должно повышать deployment target до 27. Учитывать Reduce Transparency и Reduce Motion.

## 2. Архитектура без лишних слоёв

Текущая beta использует Swift Package с executable target приложения, `UnpileCore` и `UnpileFilesystem`. `.app` упаковывает локальный скрипт: это позволяет работать с установленными Command Line Tools без полного Xcode. Отдельный модуль файлового переноса нужен для проверки отказов и журнала через контролируемый адаптер без обращения к пользовательской Корзине.

| Компонент | Ответственность | Не должен делать |
| --- | --- | --- |
| FileRecord / FileVersion | ID, относительный путь, метаданные и отпечаток версии | Содержать целиком пользовательский файл |
| SessionReducer / SessionState | Очередь, решения, Undo, переходы | Выполнять файловые операции |
| FolderAccessService | Выбор, bookmark, scoped access, отзыв | Запрашивать Full Disk Access |
| FileInventoryService | Допустимые элементы, метаданные, сортировка | Рекурсивно обходить соседние папки |
| PreviewService | Отменяемые миниатюры и Quick Look | Запускать исполняемый файл/активный HTML |
| TrashService | Проверка объекта, последовательный перенос, результат | Вызывать permanent delete при ошибке |
| SessionStore | Версионированное локальное состояние и сверка | Сохранять файлы/превью/подробные постоянные журналы |
| SwiftUI Views + ViewModel | Окна, sheet, прогресс, доступность | Вызывать trashItem прямо из жеста |

Поток: FolderAccess → Inventory → Session → Preview/решения → Review → повторная проверка → TrashService → результат → сверка Inventory.

Мутации сессии сериализованы; файловые и preview-операции вне UI-потока. Preview отменяется при смене карточки, запоздалый callback не меняет превью нового файла. Одновременное подтверждение двух пачек запрещено.

## 3. Модель данных и жизненный цикл

FileRecord содержит session ID, ID объекта/тома при наличии, относительный путь, kind/UTType, логический размер, дату изменения, признаки regular file/placeholder/hidden/link. У каждого поля есть обработка «нет данных». Не использовать время последнего открытия как доказательство ненужности.

FileVersion: идентичность объекта + значимые метаданные. При отсутствии стабильного ID не делать уверенный вывод о том, что путь с тем же именем указывает на прежний файл. Не хэшировать всё содержимое на сканировании. Metadata-only проверка не является криптографическим доказательством неизменности; эту границу учитывать при обещаниях безопасности.

Состояния элемента: undecided, kept, deferred, staged, processing, trashed, skippedChanged, failed, unresolvedAfterCrash. Состояния сессии: preparing, reviewingCards, reviewingBatch, executing, reconciling, completed/cancelled. Undo хранит предыдущие решения только до выполнения, а не обещает rollback файловой пачки.

Хранилище: небольшой versioned Codable JSON с атомарной записью в локальный контейнер приложения. Не использовать UserDefaults для массивов путей, содержимого и журнала операций. Версия схемы, обработка повреждения, миграция или безопасное предложение сбросить только состояние приложения. В beta реализованы ReviewState и ReviewStore: ограниченный JSON, относительные имена + metadata fingerprint, сверка со свежим Inventory, сохранение Undo, память Keep между сессиями и явный пересмотр. Поток локальных данных описан в [LOCAL_DATA.md](LOCAL_DATA.md).

Сохранять после каждого решения. Если запись не удалась, показывать проблему и отключать перенос до восстановления корректного состояния; не создавать скрыто несохраняемые разрушительные операции.

Перед каждой файловой операцией сохранить намерение processing; после — результат. При сбое между переносом и сохранением результата не угадывать успех по отсутствию пути: это могло быть внешнее перемещение. Такой объект получает unresolvedAfterCrash; не повторять автоматически и не относить к гарантированно перенесённым. Показывать неопределённость и предложение проверить Finder/Корзину.

После нормального завершения удалить подробное состояние успешных операций. Сохранять только необходимые решения оставленных/отложенных и незавершённые ошибки. При смене папки отменить текущую сессию, убрать её bookmark и связанные записи; не выполнять оставшиеся намерения.

## 4. Политика файлов и проверки перед переносом

1. Только непосредственные обычные файлы явно выбранной локальной папки. Скрытые по умолчанию исключены; каталоги, bundles, alias/symlinks, незавершённые загрузки и cloud placeholders исключены.
2. Проверить фактический родительский каталог, тип объекта, file/volume ID и свежие метаданные перед каждым действием. Не доверять устаревшей строке пути, строковому startsWith или ранее показанной миниатюре.
3. Не следовать симлинкам при проверках и не трогать цели ссылок. Включить тест замены обычного файла ссылкой.
4. При изменении/исчезновении объекта пропустить и потребовать повторный просмотр. При свежей записи/новой загрузке не переносить по старому решению.
5. Для конкурентных изменений использовать системную координацию файлов, где она применима, но не считать её блокировкой для всех сторонних процессов. Path-based trashItem оставляет сложность TOCTOU: исследовать её в технической пробе и честно документировать остаточную границу; не заявлять математическую гарантию отсутствия гонок.
6. Файлы «используется сейчас» нельзя надёжно определять только по отсутствию расширения .part. Не обещать универсальный детектор открытых файлов.
7. Операции последовательные и поэлементные. Нет транзакционности всей пачки, автоматического rollback или permanent-delete fallback.
8. Не модифицировать метаданные, quarantine attributes и содержимое пользовательских файлов ради работы приложения.
9. Кандидаты, отложенные или оставленные в UI, до подтверждения физически остаются на месте.

Запрещённые пути нельзя выбрать как корень обработки: системные каталоги, Library/Containers, домашний каталог целиком, root тома и системная Корзина. Не просить администраторские права. Точный allow/deny-list и определение локального тома зафиксировать после технической проверки; не превращать v1.0 в универсальный disk cleaner.

## 5. Производительность

Перечислять метаданные в фоне, загружать превью лениво, ограничить число задач и RAM-кэш. Не использовать web runtime. Не сканировать всё дерево Downloads ради размера исключённых папок.

Предварительные измеряемые бюджеты для локального SSD и синтетических fixtures: первая полезная карточка до 2 секунд на 1 000 обычных файлов; UI-реакция решения без учёта анимации до 100 мс; отсутствие зависания при 10 000 файлах; память процесса желательно до 150 МБ на стандартном наборе. Указать железо и условия, не выдавать эти цели за уже измеренные характеристики.

Метаданные отображаются до миниатюры. При большом числе файлов сортировку делать один раз на snapshot сессии; внешние добавления переходят в следующую сессию, исчезновения безопасно исключаются. Полный watcher в первой версии не нужен: refresh при активации, новый snapshot между сессиями, обязательная проверка перед переносом.

## 6. Этапы, зависимости и выходные критерии

Оценка для одного разработчика: **4–7 недель полной занятости**, с запасом на sandbox, QA и выпуск. Вечерняя работа может занять 8–14 недель или больше. Это ориентир, не обещание даты; наличие Xcode, опыта Swift и тестовых устройств пока не проверено.

| Этап | Ориентир | Результат | Выходной критерий |
| --- | --- | --- | --- |
| A. Проверка идеи и UX | 2–3 дня | Интервью, сравнение с Finder/аналогом, выбранный макет | Понятны решения и отличия; путь до проверки проходят без помощи |
| B. Техническая проба | 2–3 дня | Sandbox, bookmark, Quick Look, Trash, бесплатная локальная/ad hoc сборка | Синтетический сценарий после перезапуска работает; риски доступа названы |
| C. Ядро | 4–6 дней | Inventory, очередь, решения, Undo, хранение, сверка | Значимые регрессионные проверки проходят, нет файловых операций из UI |
| D. Нативный интерфейс | 4–6 дней | Welcome, карточки, проверка, итог, gestures/keys | Сквозной путь на синтетической папке, доступность и ошибки |
| E. Укрепление и пилот | 4–6 дней | Crash recovery, гонки, большие очереди, 5–10 beta-тестеров | Нет подтверждённых рисков потери данных; проблемы исправлены |
| F. Упаковка и release candidate | 2–3 дня | Бесплатный DMG, необходимая локальная/ad hoc подпись, README, demo, release notes | Чистая установка и фактическое первое открытие проверены, конкретный кандидат готов к одобрению |

Не переносить этап B после красивого интерфейса. На этапе D использовать синтетическую тестовую папку, а не реальные Downloads разработчика. Реальную beta применять только после безопасности и информированного выбора тестера.

## 8. Проверки

| Уровень | Что проверять |
| --- | --- |
| Ядро | Семантика keep/defer/stage, Undo, отмена, сортировка, ограничение сессии, повторный разбор изменённого файла |
| Локальное состояние | Перезапуск, атомарная запись, ошибка записи, повреждение JSON, миграция, сбой между operation/result |
| Платформа на синтетических файлах | Выбор/отзыв доступа, stale bookmarks, реальная Корзина, переименование в Корзине, ACL/locked files |
| Границы | Симлинк наружу, подмена объекта, одинаковые имена, исчезновение, placeholder, bundle, временный файл, исключённый root |
| Пачка | Нет операции до подтверждения, двойной клик, частичная ошибка, остановка, сбой после одного успешного элемента |
| Превью | Неподдерживаемый/повреждённый PDF, огромный медиафайл, отмена задачи, устаревший callback, отсутствие запуска HTML/EXE |
| Интерфейс | Welcome → разбор → проверка → итог, досрочный конец, ноль кандидатов, клавиатура, VoiceOver, Reduce Motion |
| Поставка | Минимальная/актуальная macOS, Intel/Apple Silicon, корректность выбранной подписи, установка из скачанного DMG, первое открытие без Developer ID, обновление поверх старой версии |

Автоматические интеграционные тесты не очищают реальную Корзину целиком. Любая тестовая очистка относится только к явно созданным fixtures и требует изоляции. E2E пользовательских действий сначала используют контролируемый адаптер файловых операций, отдельно ручной smoke test реального системного переноса.

Текущие проверки: `swift run UnpileChecks`, `bash scripts/build-app.sh`, GUI-проверка release-конфигурации и `codesign --verify --strict` конкретного артефакта. XCTest отсутствует в установленном CLT, поэтому проверки оформлены самостоятельным executable target без сторонних зависимостей. Для бесплатной ad hoc сборки не ожидать подтверждения trusted Developer ID от spctl. stapler относится только к отдельно выбранному нотарифицированному выпуску. Совместимость со старой macOS/Intel и полный release QA ещё впереди.

## 9. CI и безопасность поставки

- Pull requests: build + core tests + подходящие UI/платформенные проверки без signing secrets.
- Права Actions минимальны; сторонние actions закреплены по проверенным commit SHA, обновляются осознанно.
- Release: ручной запуск/защищённый environment после одобрения конкретного revision и назначения.
- В первом бесплатном релизе Developer ID certificate/private key и notary credentials не нужны. Если этот канал будет добавлен позднее, использовать только approved secret store; временный keychain на runner удаляется, секреты не логируются.
- Если позднее используются сертификаты, они недоступны workflow из fork PR и непроверенному коду. Отдельно review любых изменений workflow поставки.
- Документация, screenshots и fixtures используют вымышленные файлы; внешние diagnostics предварительно очищаются пользователем.

При подозрении на компрометацию signing key остановить выпуск, установить затронутые версии и применить процедуру отзыва/перевыпуска. План не является заявлением о формальном compliance; дополнительные требования оценивать при изменении потоков данных.

## 10. Готовность v1.0

Готово, когда основной путь и ошибки работают, meaningful checks проходят, окончательный diff проверен, UI осмотрен локально, пилотные проблемы устранены, бесплатная упаковка/совместимость и первый запуск проверены, README соответствует реальному поведению. Платная подпись и нотарификация не являются блокером готовности по текущему запросу пользователя.

Перед внешним выпуском показать: revision, значимые файлы/diff, результаты проверок, UI/screenshots, точный DMG с checksum, release notes, owner/repo/tag. **Публикация релиза или deployment выполняется только после явного одобрения этого кандидата и назначения.** Сейчас удалённых действий нет.
